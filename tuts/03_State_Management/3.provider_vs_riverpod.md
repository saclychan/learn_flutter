# 3. Cuộc Chiến Tối Thượng: Provider vs Riverpod

Sau khi trải qua nỗi đau boilerplate của `InheritedWidget`, thế giới Flutter đón nhận **Provider** (được Google khuyên dùng một thời). Nhưng rồi, chính tác giả của Provider (Remi Rousselet) lại tạo ra **Riverpod** để khắc phục những điểm yếu chí mạng của Provider.

## 🌟 1. Từ Newbie: Tại sao phải dùng thư viện?

`setState` tốt cho Local State. `InheritedWidget` giải quyết Prop Drilling nhưng code quá dài dòng. 
Provider/Riverpod sinh ra để:
1. Tách biệt Logic ra khỏi UI (Code sạch hơn).
2. Tái sử dụng Logic dễ dàng.
3. Tự động lắng nghe thay đổi và update UI hiệu quả.

## 🧠 2. Tới Senior: Provider Runtime Exception vs Riverpod Compile-Time Safety

**Nỗi đau của Provider:**
Provider dựa hoàn toàn vào `BuildContext` (và cơ chế InheritedWidget). Nếu bạn gọi `Provider.of(context)` mà trên cây Widget cha chưa cung cấp (chưa có `Provider` wrap ở trên), ứng dụng sẽ **Crash ở Runtime** với lỗi kinh hoàng: `ProviderNotFoundException`. 

**Sự tiến hóa Riverpod:**
Riverpod (đảo chữ của Provider) thay đổi hoàn toàn cuộc chơi:
- Nó KHÔNG phụ thuộc vào cây Widget (`BuildContext`) để tìm State.
- Các Provider được khai báo toàn cục (Global scope).
- Nhờ khai báo toàn cục, nếu bạn dùng sai, trình biên dịch (Compiler) sẽ báo lỗi ngay lúc bạn gõ code. Đạt được cảnh giới **Compile-Time Safety**.

## 💡 Lời khuyên từ Google / Dart Style Guide

> **Prefer** declarative state management approaches.
Nếu dự án mới, hãy chọn **Riverpod** (hoặc BLoC nếu team chuộng kiến trúc sự kiện). Riverpod hiện đang là chuẩn mực mới cho tính linh hoạt và an toàn.

## 🤕 Nỗi đau Junior (Junior Pitfalls)

Khi dùng Provider/Riverpod, lỗi kinh điển nhất là lạm dụng việc lắng nghe (watch), dẫn tới O(N) rebuilds ngầm!

❌ **SAI (Lắng nghe toàn bộ Object lớn):**
```dart
// Dùng Provider
final user = context.watch<User>(); 
// Bất cứ thuộc tính nào của User (name, age, avatar) thay đổi, widget này đều bị rebuild!
Text("Hello ${user.name}");
```

✅ **ĐÚNG (Chỉ lắng nghe đúng cái cần thiết):**
```dart
// Provider: Dùng select
final name = context.select((User u) => u.name);

// Riverpod: Dùng select
final name = ref.watch(userProvider.select((u) => u.name));
```
Kỹ thuật này giúp cắt giảm tối đa các rebuild thừa thãi, tối ưu hóa FPS của app.

## 🐛 Thử Thách Gỡ Lỗi (Intentional Bugs)

Đoạn code Provider sau có một lỗi chết người. Bạn có nhận ra không?

```dart
class MyApp extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Provider<String>(
      create: (_) => "Hello World",
      child: MaterialApp(
        home: Scaffold(
          body: Center(
            // LỖI Ở ĐÂY 👇
            child: Text(Provider.of<String>(context)),
          ),
        ),
      ),
    );
  }
}
```
**Đáp án:** Lỗi `ProviderNotFoundException`.
**Tại sao?** `context` truyền vào `Provider.of` là context của `MyApp`. Mà `MyApp` nằm TRÊN `Provider` trong cây widget, nên nó không thể tìm thấy Provider ở tổ tiên của nó.
**Cách fix:** Dùng `Builder(builder: (context) { ... })` bọc quanh `Text` để tạo ra một context mới nằm dưới `Provider`. (Với Riverpod, lỗi này vĩnh viễn không bao giờ xảy ra 🚀).
