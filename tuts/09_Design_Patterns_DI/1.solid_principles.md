# Bài 1: Bộ 5 Nguyên tắc Vàng SOLID

Có thể bạn viết code chạy được, giao diện đẹp. Nhưng sếp bảo thêm một tính năng nhỏ, bạn phải sửa file gốc 100 chỗ và lỡ tay làm gãy luôn tính năng cũ. Đó là vì bạn chưa biết SOLID. SOLID là 5 nguyên tắc sống còn để thiết kế phần mềm sạch (Clean Architecture).

> 💡 **Fun Fact:** SOLID được đưa ra bởi "Uncle Bob" (Robert C. Martin). Một câu nói nổi tiếng của ông: "Đo lường chất lượng code bằng số lần tiếng chửi thề (WTF) phát ra trong 1 phút khi review code".

## 1. S - Single Responsibility Principle (Đơn trách nhiệm)
**"Một class chỉ nên có ĐÚNG MỘT lý do để thay đổi."**

❌ **Junior (Sai):** Một Widget làm quá nhiều việc: Gọi API + Tính toán Logic + Vẽ Giao Diện.
```dart
class LoginScreen extends StatelessWidget {
  Future<void> login() async { /* Gọi HTTP request */ }
  // ... Build UI
}
```
✅ **Senior (Đúng):** Tách HTTP ra class `AuthRepository`. Tách logic quản lý ra `LoginBloc`. UI chỉ làm đúng việc vẽ UI.

## 2. O - Open/Closed Principle (Đóng/Mở)
**"Mở để mở rộng (Thêm tính năng mới), nhưng Đóng với sửa đổi (Không đụng vào code cũ)."**

❌ **Junior (Sai):** Dùng một nùi lệnh `if/else` để kiểm tra phương thức thanh toán. Thêm Momo là phải mở class cũ ra sửa, rất nguy hiểm!
```dart
void pay(String method) {
  if (method == 'cash') { /* Tiền mặt */ }
  else if (method == 'card') { /* Thẻ */ }
}
```
✅ **Senior (Đúng):** Dùng interface (abstract class) `PaymentMethod`. Khi thêm Momo, chỉ cần tạo class `MomoPayment implements PaymentMethod` mà KHÔNG CẦN đụng vào hàm `pay` gốc.

## 3. L - Liskov Substitution Principle (Thay thế Liskov)
**"Class con phải có thể thay thế hoàn toàn cho Class cha mà không làm hỏng chương trình."**

Ví dụ: Bạn có class cha là `Bird` có hàm `fly()`. Class con `Ostrich` (Đà điểu) kế thừa `Bird`, nhưng đà điểu không bay được nên bạn tung ra Exception "I can't fly" -> **Vi phạm Liskov!** Khắc phục bằng cách tách `Flyable` ra một interface riêng (Mixin trong Dart).

## 4. I - Interface Segregation Principle (Phân tách Interface)
**"Đừng bắt ai đó implement những hàm mà họ không dùng."**

❌ **Junior (Sai):** Interface `SmartDevice` có hàm `printDocument()`, `takePhoto()`, `makeCall()`. Khi tạo class `SmartWatch implements SmartDevice`, đồng hồ không in được giấy nhưng bắt buộc phải khai báo hàm `printDocument()` và để trống.

✅ **Senior (Đúng):** Xé nhỏ ra thành 3 interface: `Printer`, `Camera`, `Phone`. Đồng hồ thông minh chỉ cần implement `Phone` là đủ.

## 5. D - Dependency Inversion Principle (Đảo ngược Phụ thuộc)
**"Module cấp cao không được phụ thuộc vào Module cấp thấp. Cả hai phải phụ thuộc vào Abstraction (Interface)."**

Đây là nguyên tắc đẻ ra kỹ thuật **Dependency Injection** (Sẽ học bài sau). Không bao giờ được khởi tạo class cụ thể (cứng) bằng từ khóa `new` (hoặc khởi tạo trực tiếp) bên trong một class khác.

## 🛑 Những nỗi đau và ngộ nhận khi còn Junior
- **Nhồi nhét SOLID mù quáng:** Đôi lúc, code một dự án MVP (làm nhanh trong 3 ngày) mà chia tới 20 interface và file nhỏ lẻ, dẫn tới "Over-engineering" (Làm quá mức cần thiết). **Cách phòng tránh:** Hiểu sâu bản chất, nhưng ứng dụng linh hoạt. DRY (Don't Repeat Yourself) và KISS (Keep It Simple, Stupid) phải đi trước SOLID.

### 🚀 Mini Pet Project: Thợ săn Refactor (SOLID Refactoring)

**Yêu cầu:**
1. Tạo một class tên là `AnimalWorker` chứa 2 hàm: `eat()` và `code()`.
2. Tạo class `Human` kế thừa `AnimalWorker` -> Thực hiện được cả 2 việc ăn và code.
3. Tạo class `Robot` kế thừa `AnimalWorker` -> Robot chỉ code được chứ không biết ăn! Ép Robot ăn sẽ báo lỗi. Lúc này bạn đã VI PHẠM nguyên tắc I (Interface Segregation).
4. **Nhiệm vụ của bạn:** Refactor (Sửa lại code) bằng cách xóa class `AnimalWorker`, tạo 2 `abstract class` (hoặc mixin) riêng biệt là `Eater` và `Coder`. Sau đó cho Human implement cả 2, còn Robot chỉ implement Coder. Code của bạn đã tuân thủ chuẩn SOLID!
