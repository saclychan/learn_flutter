# Bài 2: Đo Lường & Tối Ưu Hiệu Năng (Performance Monitoring)

App không crash, nhưng user bấm nút Đăng nhập xong... 5 giây sau app mới nhúc nhích. Trải nghiệm người dùng (UX) quá tệ! Trách nhiệm của Senior là phải soi bằng được "Điểm nghẽn cổ chai" (Bottleneck) này nằm ở đâu.

> 💡 **Fun Fact:** Framework Flutter chạy trên 2 luồng (Thread) độc lập: **UI Thread** (chạy code Dart, tính toán Layout) và **Raster Thread** (Vẽ điểm ảnh bằng Skia/Impeller ra màn hình). Nếu UI Thread bị kẹt, app sẽ bị "Đứng hình" (Jank) và đánh rơi khung hình (Drop Frames).

## 1. Firebase Performance Monitoring
Nếu Crashlytics bắt lỗi văng app, thì Performance Monitoring chuyên đi đo "tốc độ". Nó tự động đo:
- Thời gian trễ mạng (API A mất 3 giây, API B mất 0.5 giây).
- Thời gian khởi động App.
- FPS (Số khung hình) của màn hình - Nếu rớt dưới 60 FPS, nó sẽ báo động.

Cài đặt bằng package `firebase_performance`.

## 2. Truy tìm Điểm Nghẽn bằng Dấu vết (Trace)
Đôi khi bạn tự viết một thuật toán sắp xếp mảng 10,000 phần tử. Bạn muốn biết chính xác CPU tốn bao nhiêu giây để chạy xong khối code đó.

```dart
import 'package:firebase_performance/firebase_performance.dart';

Future<void> sortHugeList() async {
  // 1. Tạo và bắt đầu bấm giờ một Trace
  Trace trace = FirebasePerformance.instance.newTrace('heavy_sorting');
  await trace.start();

  // Thực hiện logic nặng...
  List<int> dummy = List.generate(10000, (i) => i);
  dummy.sort();

  // 2. Dừng bấm giờ. Dữ liệu sẽ đẩy lên Server Firebase
  await trace.stop();
}
```

> 🧠 **Senior Detail:** Nếu khối code logic xử lý JSON hoặc mã hóa/giải mã quá nặng, việc đặt Trace chỉ cho bạn biết nó chậm thôi. Để CHỮA CHÁY việc UI bị đơ, Senior bắt buộc phải dời khối lượng tính toán đó sang một luồng (Isolate) khác. Bằng cách sử dụng hàm `compute` hoặc `Isolate.run()`, UI Thread sẽ được rảnh tay, App lại mượt mà 60fps!

## 3. Flutter DevTools - Máy X-Quang của Dev
Không cần chờ lên Firebase, lúc đang code ở máy, bạn có quyền năng của Chúa tể: DevTools.
Gõ lệnh hoặc bấm nút mở DevTools trong IDE. Chuyển sang tab **Performance**. Cứ mỗi khung hình bị rớt (vẽ mất quá 16ms), nó sẽ hiện cột màu đỏ chót. Bạn có thể chọc sâu vào xem hàm nào ngốn thời gian nhất!

## 🛑 Những nỗi đau và ngộ nhận khi còn Junior
- **Test hiệu năng trên chế độ Debug:** Chạy app trên máy ảo (Emulator), ấn F5 (Debug Mode). Thấy hiệu ứng chuyển cảnh giật tung chảo, cuống cuồng đi tìm cách tối ưu. **Cách phòng tránh:** ĐỪNG BAO GIỜ test FPS trên Debug Mode. Dart chạy chế độ JIT (Just-In-Time) để hỗ trợ Hot Reload nên nó rất chậm. Để test hiệu năng, phải chạy bằng lệnh `flutter run --profile` hoặc `--release` trên một CÁI ĐIỆN THOẠI THẬT.
- **Để ảnh quá to:** Load cái ảnh 4K độ phân giải 4000x4000 hiển thị vào một cái Avatar bé xíu 50x50. Mất nguyên 50MB RAM để chứa bức ảnh đó. Chuyển màn hình 2 phát là tràn RAM (OOM - Out of Memory) văng app. **Cách phòng tránh:** Dùng `cacheWidth` và `cacheHeight` của `Image.network` để Resize ảnh ngay lúc decode, tiết kiệm 95% RAM!

### 🚀 Mini Pet Project: Thợ Săn Độ Trễ

**Yêu cầu:**
1. Cài đặt package `firebase_performance`.
2. Dùng 1 API công cộng (như JSONPlaceholder). Viết 1 hàm HTTP GET khoảng 100 posts về.
3. Bọc quá trình gọi API đó bằng `FirebasePerformance.instance.newTrace('fetch_100_posts')`.
4. Ở UI có một nút "Tải dữ liệu". Bấm nút.
5. Đợi 10-15 phút để Firebase tổng hợp dữ liệu, lên Console xem Tab Performance -> Traces. Bạn sẽ thấy biểu đồ thời gian phân phối tốc độ phản hồi của khối code đó.
